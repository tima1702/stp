# Теоретическая часть

## Git Hook: commit-msg

**commit-msg hook** выполняется после ввода сообщения коммита, но до его сохранения. Он может:

- Анализировать качество сообщения коммита
- Автоматически улучшать или дополнять сообщение
- Генерировать сообщение на основе изменений в коде
- Проверять соответствие стандартам команды

### Особенности commit-msg hook:

```bash
# Расположение
.git/hooks/commit-msg

# Получает аргумент - путь к файлу с сообщением
# $1 = путь к файлу (например: .git/COMMIT_EDITMSG)

# Может изменить содержимое файла
echo "новое сообщение" > "$1"

# Коды возврата:
# 0 - успех, коммит продолжается
# любой другой - коммит отменяется
```

## Качественные commit-сообщения

### ❌ **Плохие сообщения:**

- `fix`
- `update`
- `changes`
- `wip`
- `bug fix`
- `asdf`

### ✅ **Хорошие сообщения:**

- `fix: resolve null pointer exception in user login`
- `feat: add user authentication with JWT tokens`
- `docs: update API documentation for new endpoints`
- `refactor: extract user validation logic into separate module`

## Conventional Commits

Стандарт для структурирования commit-сообщений:

```
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

### Основные типы:

- **feat** - новая функциональность
- **fix** - исправление ошибки
- **docs** - изменения в документации
- **style** - форматирование, отступы
- **refactor** - рефакторинг кода
- **test** - добавление тестов
- **chore** - обновление сборки, вспомогательных инструментов

### Примеры:

```
feat(auth): add JWT token validation
fix(api): handle empty response in user service
docs(readme): update installation instructions
refactor(utils): simplify date formatting function
```

## Анализ git diff

Для генерации сообщений нужно анализировать изменения:

```bash
# Получить изменения для staged файлов
git diff --staged

# Краткая статистика изменений
git diff --staged --stat

# Только имена измененных файлов
git diff --staged --name-only

# Изменения в определенном файле
git diff --staged filename.py
```

## 3. Пошаговая реализация функций

### Шаг 1: Функция проверки Ollama

```bash
check_ollama() {
    echo -e "${BLUE}🔗 Checking Ollama availability...${NC}"
    
    if ! curl -s "$OLLAMA_URL/api/tags" >/dev/null 2>&1; then
        echo -e "${YELLOW}⚠️  Ollama not available, using original message${NC}"
        log_message "WARNING: Ollama not available"
        return 1
    fi
    
    log_message "INFO: Ollama is available"
    return 0
}
```

### Шаг 2: Функция чтения сообщения

```bash
read_commit_message() {
    if [ ! -f "$COMMIT_MSG_FILE" ]; then
        echo ""
        return 1
    fi
    
    # Удаляем комментарии и пустые строки
    grep -v "^#" "$COMMIT_MSG_FILE" | grep -v "^$" | head -1
}
```

### Шаг 3: Функция получения изменений

```bash
get_changes_info() {
    local changes_summary
    local changed_files
    local diff_sample
    
    # Статистика изменений
    changes_summary=$(git diff --staged --stat 2>/dev/null || echo "No changes")
    
    # Список файлов
    changed_files=$(git diff --staged --name-only 2>/dev/null | head -5)
    
    # Образец изменений (первые 10 строк)
    diff_sample=$(git diff --staged 2>/dev/null | head -20)
    
    echo "Files: $changed_files. Changes: $changes_summary. Sample: $diff_sample"
}
```

## 5. Тестовые сценарии

```bash

```

**Ожидаемое поведение:**
- Hook обнаруживает плохое сообщение
- Анализирует изменения (новый файл с функциями)
- Предлагает улучшенное сообщение
- Показывает интерактивный выбор

```bash

```

```bash
git add src/user.py
git commit -m "feat(user): add User class with display name functionality"
```

**Ожидаемое поведение:**
- Hook определяет, что сообщение уже хорошее
- Не предлагает изменения
- Разрешает коммит
